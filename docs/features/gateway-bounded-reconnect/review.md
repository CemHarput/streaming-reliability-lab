## Findings
No blocker, major or minor finding. Two optional nits remain; neither blocks.

### nit-1: the `requested == 0` check in `claimWhileTheRetryCallIsStartingCancelsIt` proves nothing
`StreamBridgeRetryTest.java:706`
- The test delivers and writes no chunk, so `handBackCredit` never runs, `banked` stays 0 and `markStarted` (`StreamBridge.java:266-283`) never calls `request`. The check therefore does not test "a cancelled call is given no credit". The test's real purpose, the cancel inside the STARTING window (`:699`), is not affected.
- Optional: remove the check, or have a chunk written before the latch is released.

### nit-2: the real margin of the `during` window in `idleCannotFireDuringBackoff` is about 3.7x
`StreamBridgeRetryTest.java:751-762`
- `during(600ms)` is a fifth of the backoff, but with the preceding await (about one poll) and the last poll of `during` the window closes about 0.7-0.8 s after the backoff was scheduled; the backoff fires at 3 s. The first-pass suggestion "idle window at most a fifth of the backoff" is met. The test would only break if the test thread stalled for about 2 s.

## Verification of the first-pass findings (by reading source)
- **P2-1 fixed.** `deliver` and `onError` run back to back on one thread (`:748-749`). `chunkReceived` arms IDLE at 100 ms (`StreamTimer.java:89-91`); `onError` then synchronously does `retryAfter`: under `creditLock` it sets `state = DEAD` and `callEnded` removes the idle timer (`StreamBridge.java:345-351`), then `scheduleRetry` sets the 3 s backoff (`:356`). That work takes microseconds to a few milliseconds (offer, virtual thread start, `isAccepting`): more than 100x margin against 100 ms. The drainer's `handBackCredit` cannot arm anything either way: before `callEnded` the slot is occupied so it does not re-arm (`StreamTimer.java:108`); afterwards the state is DEAD and it is a no-op (`StreamBridge.java:490`). `nextSeq = 1` is written before the offer (`:294`), so the `resume_from_seq == 1` check holds. First await: `retryPending` is already true synchronously; the idle timer was cancelled and `removeOnCancel` is on (`StreamTimeouts.java:75`), so `pendingTimers == 1`. Last await (`atMost` 15 s against about 3 s, 5x): the new call's `timer.start(4)` arms FIRST_CHUNK at 30 s, so `timerArmed` is true and `retryPending` false; the fired backoff left the queue so only the first-chunk task is there; `retries{resume}` is incremented before `startCall` (`:399`).
- **P2-2 fixed.** The three tests complement each other.
  - (a) `clientGoneCancelsTheLiveRetryCallNotTheDeadOne`: if `cancelUpstream` wrongly cancelled `initialAttempt.call`, `:673` (`call(0).cancelMessage == null`) would always fail. Awaitility may see `calls.size() == 2` between `calls.add` and `beforeStart`; the cancel then comes from the Dekker branch with the same "client disconnected" result, so the test is deterministic in both orders.
  - (b) `claimWhileTheRetryCallIsStartingCancelsIt`: `onStart` waits on the `release` latch after `beforeStart` and before `markStarted`, which really is the STARTING window. The claim finds `current.call` published. A mutation that cancels the wrong attempt leaves `call(1).cancelMessage` null and fails the test; the Dekker branch cannot mask it because it ran before the claim. The latch is opened in `finally` (`:711`) and in `tearDown`.
  - (c) `claimBeforeTheRetryCallsBeforeStartCancelsItInsideBeforeStart`: the hook runs on the `stream-retry` thread after `current = attempt2` and before `call` is published. `cancelUpstream` sees null; the cancel can only come from `attemptBeforeStart:259-262`. If that branch were deleted the test would fail for certain. Single thread, no race.
  - Implicit assumptions hold: `FakeUpstream.cancel` uses `compareAndSet(null, ...)` so the first message stays and both paths write the same one; `immediate(3)` with jitter `b -> 0` gives `Duration.ZERO` and fires at once; starts are sequential so the `CopyOnWriteArrayList` order is exact.
- **P3-1 fixed.** Every sentence of the README "Stops" bullet (README:327-335) matches the code: each claim cancels the backoff through `timer.close()` (`StreamBridge.java:633-639`); the start of shutdown does not cancel a wait in progress; when the wait ends `startAttempt:386-389` calls `recordEnd(lastStatus)` and the stream ends with UNAVAILABLE; an UNAVAILABLE seen during drain is recorded at once through `retryAfter:335-337`; the wait lasts at most `max-backoff`, and if `max-backoff > drain-timeout`, `awaitEmpty` times out, then `cancelAll` -> `cancelForShutdown` ends it with CANCELLED. The `shutdown|drain` scan found no other contradicting sentence; Known limits lines 355 and 358 agree. `plan.md` AC6 still carries the old wording; the plan is hash-locked and the deviation is documented in implementation.md, so the reviewer did not count it as a new finding.
- **P3-2 fixed.** The task runs on the `stream-timeouts` scheduler thread; `supplyAsync` is run by a different thread (the common pool, or a separate thread if parallelism is below 2). `isArmed()` takes `timerLock` (`StreamTimer.java:188-195`). If `fire` ran the task under the lock, `get(2s)` would throw `TimeoutException`, `probeFailure` would be set, `ranWithoutLock` would stay false and the test would fail after the 5 s await. It would also fail if the task never ran. Flake risk is low: expected time is microseconds against a 2 s limit.
