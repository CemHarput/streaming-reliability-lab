# Request: benchmark-report

Goal
Turn a raw benchmark result set produced by the bench runner (bench/results/<run-id>/: manifest.json, per-run loadgen JSONL and summary, gateway/simulator snapshots) into a reproducible, honest report: a tool that reads a result set and writes derived tables (and simple charts), plus a written report document that states what was measured, under which conditions, and what can and cannot be concluded. The report describes observations from ONE named result set on ONE machine. It must not claim that either connection mode is generally better, faster or cheaper.

Context
- Existing: bench module (runner, manifest schema v1 with protocolVersion 1, flags dictionary, protocol in docs/benchmark-protocol.md), loadgen (JSONL schema v1: header, request records with outcome/ttfb/ttfc/total/inter-chunk fields, footer with inter-chunk histogram, summary JSON), gateway metrics snapshots (rejected_total, active_streams, queue_depth, timeouts, retries, connection_mode), simulator stats. docs/benchmark-protocol.md lists what the protocol cannot answer; the report must repeat and respect those limits.
- The real result set will be produced by the user on a quiet Linux machine (a dedicated-core VM or an idle separate computer), NOT on the Windows developer machine, and brought back as an archive (tar.gz of bench/results/<run-id>) that is extracted locally and NOT committed. The analyzer therefore must handle the Linux variants of the recorded environment (cpu model from /proc/cpuinfo, power plan null, ss-based TIME_WAIT, SIGTERM-based stop methods in manifest process stop records) and must work on a Windows developer machine reading a result set from Linux (path separators, line endings). The harness was only run on Windows so far: if the analyzer or the manifest turn out to miss something needed for Linux results (fields recorded as null, unknown flags, different stop methods), the planner must list it as a finding for the runner rather than change the runner here.
- Planner: read docs/benchmark-protocol.md, bench manifest/flags code, loadgen RecordWriter/Summary and the real shape of a smoke result under bench/results/ (smoke outputs exist only to learn the file shapes; they are tiny, partly produced by failure scenarios, and must NOT be used as report data or committed). Decide where the analyzer lives (a subcommand or class in the bench module reusing its Json classes vs a new module; avoid new heavy dependencies; Java 26, Maven multi-module, no Python/R unless justified) and how it is invoked from the command line.
- No measured result set is committed and none exists yet in final form. The user will name its run-id/path when implementation starts. Until then the analyzer must be fully testable with synthetic fixture result sets generated in tests (small, hand-built, clearly artificial), and docs/benchmark-report.md must be written so it can be generated from a real set without hand-editing numbers.

Analysis rules (honesty requirements; planner to turn into precise definitions)
- Unit of analysis: one measured run (mode, concurrency, repetition). Warm-up runs are excluded from comparisons but listed. Runs with flags that invalidate comparison (failed/interrupted/not_run status, LOADGEN_*, *_EXITED, CONNECTION_MODE_MISMATCH, PORT_NOT_FREED, CPU_BUSY_BEFORE_RUN, log truncation, etc.: planner to classify flags into 'exclude', 'caution', 'info') are reported, never silently dropped; the report shows exactly which runs entered each comparison and why others did not.
- Metrics per run: outcome counts and shares, completed streams per second (definition stated), time to first chunk and total stream duration distributions (HdrHistogram or exact percentiles from the JSONL; p50/p90/p99/max and count), inter-chunk gap distribution from the footer histogram, rejected count and share, gateway/simulator snapshot deltas. State precisely how each metric is computed and its caveats (ttfb is headers-received, buffer-arrival resolution, closed model coordinated omission, the 503 reject-pause think time).
- Comparison between modes only within the same concurrency, and only as observations: show per-repetition values side by side, median and min-max across repetitions, and the order position (A/B in ABBA) of each repetition so order/drift effects are visible. With 4 repetitions per cell do not report p-values or confidence claims; if a spread measure or a simple effect-size description is used, say why it is only descriptive. State when the ranges of the two modes overlap, and when the spread across repetitions within one mode is as large as the difference between modes (then the report must say the set cannot separate them). Never rank, never say 'better/faster' in general; sentences such as 'in this result set, at concurrency 50, the median ttfc of mode X was higher than that of mode Y; ranges did (not) overlap' are the allowed style.
- Cross-checks reported as a data-quality section: manifest consistency (counts in summary vs JSONL vs footer), environment recorded (machine, git commit/dirty, artifacts sha256), checklist answers, CPU-load samples, TIME_WAIT counts, GC logs only if cheaply usable (otherwise listed as not analysed).

Outputs
- docs/benchmark-report.md (English, generated or semi-generated from the tool so numbers cannot drift from data; planner decides the mechanism: tool writes markdown from a template, human-written prose sections kept separate from generated tables, with an identification block: run-id, commit, dirty flag, machine summary without absolute paths or user names or cloud account identifiers).
- Derived data that may be committed: small summary tables (CSV/JSON/markdown) and simple static charts (e.g. SVG written by the tool itself or plain markdown tables; no external services, no network, no heavy chart library unless justified). The raw bench/results stay uncommitted; document how a reader can regenerate the report from an archived result set.
- The tool prints a short machine-readable and human-readable summary of what it read and what it excluded; exit codes: 0 success, 2 usage/invalid input, 1 unexpected error; refuses to analyse a manifest with an unsupported schemaVersion/protocolVersion; never modifies the result set.

Tests and verification
- Unit tests with synthetic result sets built in test code (several runs per mode and concurrency incl. a flagged run, a failed run, a rejected-heavy run, an incomplete/interrupted set, a Linux-flavoured environment block, a malformed JSONL line, a manifest with an unsupported version): percentile computation against hand-computed values, flag classification, exclusion reporting, ABBA order labelling, side-by-side output, markdown/SVG generation (small stable golden files), no absolute paths/user names in generated output, deterministic output (same input -> byte-identical output), bounded memory for large JSONL (stream, do not load everything) with a size-bounded test. ./mvnw -B verify stays green; no real gateway/simulator is started.
- A manual run on the real result set named by the user is the final step. If no real set is available when implementing, the implementer stops after the tool and tests, leaves docs/benchmark-report.md as a generated placeholder clearly stating 'no result set analysed yet' (no numbers), and reports that as the remaining step.
- Acceptance criteria (planner to refine and number): analyzer reads the documented schemas and refuses unsupported versions; all exclusion/caution rules applied and visible in the output; allowed-statement style enforced (a test scans the generated report for forbidden phrases such as 'faster than', 'better', 'outperforms', 'wins' outside quoted limits sections and fails); report states the limits of the protocol; reproducibility instructions in README/protocol docs; no raw results or absolute paths committed.

Out of scope
- New measurements, changing or re-running the bench runner, loadgen, gateway, simulator or proto; open-model load; statistical inference beyond descriptive summaries; recommendations about production use; CPU pinning; MQTT; showcase/portfolio write-up (comes after, using the generated report).

Constraints
- Work on main, no new branch, no commits or pushes. Do not use or commit data from the smoke result directories.
